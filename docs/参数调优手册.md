# 参数调优手册

《摩天叠楼师》的全部手感与难度参数集中在 **`js/core/config.js`** 一个文件里。改完任何参数，都请按下面的流程验证。

## 0. 怎么调、怎么验

```
1. 改 js/core/config.js
2. node tests/run-tests.js        # 参数自检 + 139 个用例
3. 用微信开发者工具打开工程目录，试手感
```

第 2 步不是形式。`js/core/validate.js` 会拦下**逻辑上自相矛盾**的配置——这类问题在开发者工具里不报错，只表现为"手感很怪、但说不上哪里怪"，靠肉眼试是查不出来的。它能抓：

- 振幅 ≥ 摆臂长（摆角无解，吊车几何直接失效）
- 失误容差偏离楼层半宽（破坏判定与物理的一致性）
- 完美容差 ≥ 失误容差（一般落点区间消失，三档判定退化成两档）
- 难度曲线反转（最小周期 > 起始周期，塔越高摆得越慢）
- 吊点高度 < 摆臂长（吊绳穿到塔顶下面去了）
- 振幅 < 两层坍塌阈值（吊车够不到能让塔倒的位置，局面变成必得分）
- 负的高塔惩罚（难度曲线反向）
- 坍塌比例越出 (0, 1]
- 失误额度 ≤ 0
- 地基比楼层窄

测试里还有两条**防死配置**的静态检查：config 里定义了但无人读取的参数会被报出来；代码里引用了 config 中不存在的字段（多半是拼错）也会被报出来。

## 1. 铁律：一处不要动

### `TOLERANCE.missRatio` 必须等于 `0.5`

```
失误容差 = FLOOR.width × missRatio = 64 × 0.5 = 32 = 楼层半宽
```

`0.5` 不是随手取的数，它**等价于「落点中心越过下层支承边缘」**——楼层会真的翻落下去的物理临界点。

改动它会同时破坏两件事：判定说"这层放上去了"，而物理上它该掉下去。玩家会看到楼层悬空。要放宽容错，请改 `FOUNDATION.width` 或 `STABILITY.collapseRatio`（它们只影响稳定性判据，不碰物理），不要动这里。

## 2. 派生量速查

调参前先算清楚这几个量，它们决定了容错空间的形状。

| 派生量 | 公式 | 当前值 |
|---|---|---|
| 完美容差 | `FLOOR.width × perfectRatio` | `64 × 0.18` = **11.52** |
| 失误容差 | `FLOOR.width × missRatio` | `64 × 0.5` = **32**（= 楼层半宽） |
| 坍塌阈值(n 层) | `FOUNDATION.width / 2 × collapseRatio × 1/(1 + (n-1) × topHeavyGain)` | 见下表 |
| 摆动周期(n 层) | 从 `periodSecAtStart` 线性收紧到 `periodSecAtMin`，在 `periodRampFloors` 层处到最紧 | 第 1 层 2.2s → 第 30 层起 1.5s |

坍塌阈值随塔高的实际变化：

| 楼层数 | 收紧系数 | 坍塌阈值 |
|---|---|---|
| 1 | 1.000 | 40.30 |
| 2 | 0.943 | 38.02 |
| 5 | 0.806 | 32.50 |
| 10 | 0.649 | 26.17 |
| 20 | 0.467 | 18.83 |
| 30 | 0.365 | 14.71 |

**这张表是理解难度的钥匙。** 注意 30 层时坍塌阈值（14.71）已经非常接近完美容差（11.52）：到了那个高度，连续两层都擦着完美线的边缘落，塔就会倒。

## 3. 逐参数说明

### 3.1 世界与坐标系 `WORLD`

> 坐标系约定：世界宽度固定 `WORLD.width` 个逻辑单位，高度按设备长宽比自适应。世界原点在地面中线，x 向右为正、范围 `[0, WORLD.width]`；y **向上**为正、地面为 0。在 375 宽的设备上，1 个世界单位 = 1 个 CSS 像素。

| 参数 | 值 | 作用 | 调大 | 调小 |
|---|---|---|---|---|
| `width` | 375 | 世界宽度，同时是所有水平尺度参数的基准 | **不建议改**。改了要重算 `centerX`、`amplitude`、`groundBaselineOffset` 的合理值 | 同上 |
| `groundBaselineOffset` | −80 | 摄像机的初始位置（屏幕底边对应的世界 y）。也是摄像机的下界 | 地面在屏幕上更靠上，开局能多看到塔身；但空地基会显得悬空 | 地面更靠下，开局视野更空 |
| `cameraLerpRate` | 4.2 | 摄像机跟随的指数逼近速率（每秒） | 镜头跟得更紧、反应更快；太大则塔升高时画面有"被拽"的突兀感 | 镜头更迟滞、更柔和；太小则塔顶会跑出屏幕 |

### 3.2 地基与楼层 `FOUNDATION` / `FLOOR`

| 参数 | 值 | 作用 | 调大 | 调小 |
|---|---|---|---|---|
| `FOUNDATION.width` | 130 | 地基宽度。**直接决定容错空间**——坍塌阈值与它成正比 | 容错变宽，塔更难倒，整体更宽容 | 容错收紧，更早坍塌，更紧张 |
| `FOUNDATION.height` | 6 | 地基的视觉厚度。它已并入地面，只是一条铺装带 | 只是一条铺装带变厚 | 太薄会看不出它是铺装 |
| `FLOOR.width` | 64 | 楼层宽度。**同时决定完美容差与失误容差**（都是它的比例） | 两个容差同步放大 → 整体更容易 | 两个容差同步收紧 → 整体更难 |
| `FLOOR.height` | 64 | 楼层高度。等于宽度，所以每层是一个方块（与原版一致）。**它不参与任何判定** | 一屏能看到的层数变少、摄像机跟随更早 | 一屏层数变多，塔显得细长 |
| `FLOOR.radius` | 2 | 楼层圆角半径 | 更圆润，但会滑向"积木" | 更硬朗建筑感；取 0 会硬到割裂每层轮廓 |

> ⚠️ `FLOOR.width` 是"全局难度旋钮"——它同时改变完美容差和失误容差，两个一起动。想只改其中一个，请改 `TOLERANCE` 里的比例。

### 3.3 吊车与钟摆 `CRANE`

这是真正的钟摆几何，不是水平平移。吊点固定在 `(centerX, 塔顶 + pivotHeightAboveTop)`，摆臂长 `pendulumLength`：

```
水平位置   x = centerX + amplitude × sin(ωt)
摆角       φ = asin(amplitude / pendulumLength × sin(ωt))
摆动周期   ω = 2π / 当前周期(塔高)
```

渲染层直接拿 `φ` 去画吊绳角度，所以**逻辑与视觉共享同一份几何，永远不会脱节**。

| 参数 | 值 | 作用 | 调大 | 调小 |
|---|---|---|---|---|
| `centerX` | 187.5 | 吊点水平位置，也是摆动的中轴 | 塔的地基中心也跟着定在这里，改它要一起改地基布局 | 同上 |
| `amplitude` | 118 | 摆动振幅（单向，世界单位） | 摆幅更大、够得更远，塔偏离中线时更容易补救 | 摆幅更小、更集中在中心，更容易稳定 |
| `periodSecAtStart` | 2.2 | 开局时的摆动周期（秒） | 开局更慢、更好瞄 | 开局就很快，新手劝退 |
| `periodSecAtMin` | 1.5 | 塔长到 `periodRampFloors` 层后的周期下限 | 后期不那么紧张 | 后期非常紧张，是主要的难度来源 |
| `periodRampFloors` | 30 | 用多少层从起始周期收紧到最小周期 | 难度爬升更慢、更平缓 | 难度爬升更快、更陡 |
| `pivotHeightAboveTop` | 250 | 吊点位于塔顶上方多高 | 吊点更高，吊绳更陡、视觉更清楚；但更占屏幕纵向空间 | 吊点更低；**必须大于 `pendulumLength`，否则吊绳会穿到塔顶下面** |
| `pendulumLength` | 165 | 摆臂长 | 摆角更小（同样的水平位移），摆得更"平" | 摆角更大，两端抬升更明显；**必须大于 `amplitude`，否则摆角无解** |
| `dropGravity` | 2400 | 下落重力加速度（世界单位/秒²） | 下落更快、"手感更重"；太快则玩家来不及看清 | 下落更慢、更飘 |

**这三个约束是硬性的**（`validate.js` 会拦）：
- `amplitude < pendulumLength`
- `pivotHeightAboveTop > pendulumLength`
- `amplitude > 两层坍塌阈值` —— 否则吊车够不到能让塔坍塌的位置，局面变成必然高分

### 3.4 判定阈值 `TOLERANCE`

| 参数 | 值 | 作用 | 调大 | 调小 |
|---|---|---|---|---|
| `perfectRatio` | 0.18 | 完美容差 = `FLOOR.width × 0.18` = 11.52 | 完美判定更容易，连击更容易攒，正反馈更频繁 | 完美更难，连击成了稀缺资源 |
| `missRatio` | 0.5 | 失误容差 = `FLOOR.width × 0.5` = 32 | **不要动**，见第 1 节 | 同上 |

> `perfectRatio ≥ missRatio` 会被自检拦下——那样"一般落点"区间为空，三档判定退化成两档。

### 3.5 稳定性 `STABILITY`

判定用的是**重心偏心**，不是累积偏移和：`偏心 = |塔的重心 − 地基中心|`。左右往复堆叠的塔在"累积偏移和"模型下会被误判为危险，而重心模型不会——这条有专门的回归测试钉住（`tests/tower.test.js`）。

| 参数 | 值 | 作用 | 调大 | 调小 |
|---|---|---|---|---|
| `collapseRatio` | 0.62 | 坍塌阈值 = `地基半宽 × 0.62 × 高塔收紧系数` | 更宽容，塔更抗偏 | 更严格，偏一点就倒 |
| `topHeavyGain` | 0.06 | **高塔惩罚**。收紧系数 = `1/(1 + (n-1) × gain)` | 高塔明显更危险，后期压力陡增 | 高塔惩罚减弱；**设 0 即完全关闭** |
| `swayDecayPerSec` | 1.6 | 视觉摇摆强度的衰减速率 | 摇摆很快平静下来，警示作用减弱 | 摇摆持续更久，视觉上更"不稳" |
| `swayPerMiss` | 0.55 | 每次失误给视觉摇摆加多少 | 失误的视觉冲击更强 | 失误看起来更轻描淡写 |
| `swayPerImperfect` | 0.18 | 每次一般落点给视觉摇摆加多少 | 一般落点也会让塔明显晃起来 | 一般落点几乎不晃 |

> **为什么需要 `topHeavyGain`？** 重心是各层位置的平均值，所以"多加一层"对重心的撬动是 `1/n`——塔越高，单次坏落点的影响反而越小。物理上没错，但作为难度曲线是**反的**。这个系数是刻意加的手感补丁，不是物理定律。手册里保留它是为了让后来者知道：这行代码不是从物理推出来的，别试图"修正"它。

> ⚠️ `sway*` 三个参数**只影响视觉**，不参与判定。摇摆强度是纯表现层状态（`tower.sway`），判定只读偏心。不要试图靠调摇摆来改难度。

### 3.6 局面与连击 `RUN` / `COMBO`

| 参数 | 值 | 作用 | 调大 | 调小 |
|---|---|---|---|---|
| `RUN.missBudget` | 3 | 一次局面允许的失误次数上限。用尽即**封顶** | 更宽容，能玩更久 | 更硬核；设 1 就是"一次失误就结束" |
| `COMBO.maxSteps` | 20 | 连击计数上限 | 连击可以堆得更高，人口加成上限也更高（受 `comboCap` 限制） | 连击更早封顶 |

> 连击规则：**完美落点递增、一般落点保持、失误清零**。一般落点不打断连击是这套规则的核心——多数投放都落在"差一点点就完美"的区间，正是张力来源。这条有单元测试直接钉住。

### 3.7 人口与得分 `POPULATION` / `SCORE`

```
单层人口 = basePerFloor × (1 + comboStepBonus × min(连击数, comboCap))

得分 = 层数 × perFloor
     + 最佳连击 × comboBonusPerStep
     + 人口 × populationFactor
     若坍塌：再 × (1 - collapsePenalty)
```

| 参数 | 值 | 作用 | 调大 | 调小 |
|---|---|---|---|---|
| `basePerFloor` | 2 | 每层的基础人口 | 人口涨得更快，人口项在得分里权重更大 | 人口增长更缓 |
| `comboStepBonus` | 0.35 | 每级连击给的人口加成 | 连击的经济价值更高，鼓励追完美 | 连击只影响得分，不影响人口 |
| `comboCap` | 8 | 人口计算时连击数的封顶 | 高连击的收益继续增长，利于高手 | 高连击收益封顶更早，曲线更平 |
| `perFloor` | 10 | 每层得分 | 堆高比追连击更划算 | 连击/人口更划算 |
| `comboBonusPerStep` | 5 | 每级最佳连击的得分 | 追完美更划算 | 堆高更划算 |
| `populationFactor` | 0.5 | 人口的得分权重 | 人口（长期属性）对得分影响更大 | 人口不影响得分 |
| `collapsePenalty` | 0.35 | 坍塌时的得分折扣 | 坍塌代价更大（0.5 即打五折） | 坍塌代价更小；**设 0 则坍塌不扣分** |

> **封顶与坍塌在得分上不对等**：封顶保留塔身、不打折；坍塌摧毁塔身、打 35% 折扣。这个差异是刻意的——两种失败的性质不同，见 `docs/adr/0004-topped-out-vs-collapsed.md`。

### 3.8 摄像机 `WORLD.cameraLerpRate` / `CAMERA`

| 参数 | 值 | 作用 | 调大 | 调小 |
|---|---|---|---|---|
| `topPadding` | 60 | 塔顶之上（再往上算上吊车几何）必须留出的世界高度 | 塔顶离屏幕顶部更远、更安全；但占用纵向空间、塔显得小 | 塔顶更靠近屏幕顶边；**太小则吊车会顶到状态栏** |
| `followRatio` | 0.8 | 摄像机目标点落在屏幕纵向的哪个比例处 | 塔看得更多；但吊车轨道会上移、与 HUD 撞车 | 塔在屏幕上更靠下、吊车空间更充裕 |

> `followRatio` 同时决定两件事：屏幕上方留多少空间给吊车、以及吊车轨道落在哪一行。改它之后请务必看一眼 HUD 是否与轨道重叠。

### 3.9 观感 `VISUAL`

| 参数 | 值 | 作用 | 调大 | 调小 |
|---|---|---|---|---|
| `leanVisualGain` | 0.85 | 倾角的视觉放大系数。1 = 完全按几何倾角绘制 | 塔歪得更夸张、预警更强烈；**超过 1 会夸大危险，让玩家误判** | 塔看起来更直，预警变弱；设 0 则完全不倾斜 |
| `swayAmplitude` | 5.5 | 摇摆的视觉幅度（世界单位） | 塔晃得更明显 | 几乎不晃 |
| `swayHz` | 3.4 | 摇摆频率 | 抖得更快、更"紧张" | 晃得更慢、更"沉重" |
| `landingSquash` | 0.16 | 落地时楼层被压扁的最大比例 | 落地更有"重量感" | 更轻飘 |
| `landingSquashSec` | 0.1 | 压扁回弹时长（秒） | 回弹更从容 | 回弹更快；**必须短于 `FEEL.settleDelaySec`**，否则下次投放时楼层还扁着、会露出缝 |
| `missShakePx` | 7 | 失误时画面抖动幅度（像素） | 冲击更强烈 | 更含蓄；设 0 则关掉抖动 |
| `missShakeSec` | 0.22 | 失误抖动时长。坍塌时用 `× 2.2` | 抖动持续更久 | 一闪而过 |
| `collapseSec` | 0.65 | 坍塌倒塌动画时长（秒） | 倒得更慢、更有"垮掉"的过程感；**超过 1.5 会显得拖沓，结算面板早就在等了** | 更快；设 0 则瞬间倒满 |
| `collapseSweepDeg` | 18 | 坍塌时叠加在派生倾角之上的额外倒塌角（度） | 倒得更狠；**太大塔尖会转出画面** | 更含蓄；**设 0 等于关掉倒塌演出，只剩抖动与红字** |

> **`collapseSec` / `collapseSweepDeg` 是唯一一组不碰内核的观感参数。** 内核的 `leanAngle` 是由偏心算出的**派生量**，渲染层只读；这里给的是「倒了多少」这个纯演出量，两者相加才是画面上的总倾角。所以调它们不会影响任何判定，也不该被任何判定读取（见 `docs/adr/0005`）。
>
> 倒塌是绕**倾倒那一侧的地基边缘**转的，不是绕中线 —— 绕中线会让塔的一角扎进地面，看起来像整座塔陷下去而不是倒下去。这条几何契约由 `tests/render.test.js` 的「倾倒侧底角不会扎进地面」钉住。

### 3.10 帧循环 `FEEL`

| 参数 | 值 | 作用 | 调大 | 调小 |
|---|---|---|---|---|
| `fixedDt` | 1/60 | 逻辑定步长。物理推进固定用它，与帧率解耦 | 逻辑更省 CPU；太大则高帧率下手感变粗糙 | 逻辑更细腻；太小则低端机 CPU 吃紧 |
| `maxFrameDt` | 1/20 | 单帧最大步长，防止切后台回来一次跳太多 | 卡顿后追得更快；太大会出现"一跳到底" | 更保守；太小则在低帧率设备上逻辑比真实时间慢 |
| `settleDelaySec` | 0.12 | 落地后停顿多久才允许下一次投放 | 有更多喘息与观察时间 | 节奏更快；**不能小于 `landingSquashSec`** |

> `fixedDt` 与 `maxFrameDt` 的关系决定了"单帧最多推进几步"：`maxFrameDt / fixedDt = 3`。代码里还有一层硬上限 `MAX_LOGIC_STEPS_PER_FRAME = 8`（在 `js/game.js`），超过就丢弃余量——宁可掉帧也不滚雪球。

### 3.11 反馈开关 `AUDIO` / `VIBRATE` / `TUTORIAL`

| 参数 | 值 | 作用 |
|---|---|---|
| `AUDIO.enabled` | true | 总开关。关闭后 `createSfx` 直接返回空实现，不再创建音频上下文 |
| `AUDIO.masterVolume` | 0.45 | 主音量（0~1） |
| `VIBRATE.enabled` | true | 震动总开关。关闭后任何落点与终局都不再震动 |
| `TUTORIAL.enabled` | true | 新手引导开关 |
| `TUTORIAL.minFloorsToHide` | 2 | 建到这么多层后隐藏引导（立即消失，无淡出） |

> 这几项都是**真开关**，有测试保证关掉之后行为真的改变（不是"存着但没人读"的死配置）。

### 3.12 视觉主题 `js/render/themes.js`（不在 config 里）

配色、天空、城市、楼层色板**全部不在 `config.js`**，而在 `js/render/themes.js`。

这是刻意的：`config.js` 是内核的文件，而内核不知道 Canvas 存在——把配色塞进去等于让内核依赖渲染（见 `docs/adr/0006`）。所以**本节是这本手册里唯一不属于 config 的一节**，它不参与任何判定，改它不会影响手感与难度。

#### 三套主题

| 主题 | 取向 | 天体 | 云 | 星辰 | 城市 | 地面 |
|---|---|---|---|---|---|---|
| `day` 晴日 | 明亮清爽，**云的层次是主角** | 太阳高挂 `y 0.20` | 12 朵，白色受光面 + 浅蓝背光面 | 关 | 4 段冷灰蓝，**不点灯** | 草绿 |
| `dusk` 黄昏（默认） | 逆光剪影 + 被夕阳染色的云，**层次最强** | 太阳贴地平线 `y 0.74` | 13 朵，暖橙受光面 + 紫灰背光面 | 26 颗 | 越近越深，城市成剪影 | 深紫灰 |
| `night` 夜晚 | 深空 + 星辰 + **万家灯火**，与「建造城市」的主题最贴 | 月亮 `y 0.22` | 9 朵，低对比 | 120 颗 | 星空蓝，窗灯密度 0.34 | 近黑蓝 |

#### 换主题

```js
// js/render/themes.js
const DEFAULT_THEME = 'dusk';          // 改成 'day' 或 'night' 即可全局生效
```

需要按局面切换时用 `themes.themeByName(name)` 取一套完整主题对象传下去（`themes.js` 已导出）。`palette.js` 只是「当前用哪套」的出口，渲染层其余模块统统 `require('./palette')`，**换皮肤不需要改动任何一行绘制逻辑**。

不认识的主题名会回落到 `dusk`，不会报错、也不会画成空白。

#### 主要字段

| 字段 | 作用 | 要注意 |
|---|---|---|
| `sky.stops` | 天空竖向渐变，`[位置比例, 颜色]` 数组 | **至少要 3~5 段**。只有两段就是"整屏大面积纯色留白"，这正是改版前「简陋感」的最大来源 |
| `celestial` | 天体：`kind` / `x` / `y` / `radius` / `core` / `rim` / `glow` / `glowScale` | `x` `y` 是**屏幕高度比例**，不随镜头移动——天体是远景，机位升高时它在画面里的位置本就不该动 |
| `clouds` | `count` / `lit` / `shade` / `bandTop` / `bandBottom` / `minW` / `maxW` | `bandTop` / `bandBottom` 是云带的纵向范围；云底由程序生成，不用手工排 |
| `stars` | `enabled` / `count` / `color` | 白天主题必须 `enabled: false`，否则天空亮着还满天星 |
| `skyline` | `far` / `mid` / `near` 三层城市色 + `windows` | `windows` 设 `null` 就是不点灯（白天）；`ratio` 是亮灯比例 |
| `ground` | `top` / `bottom` / `edge` | 环境色。**不要比塔身更饱和**——整幅画里最鲜艳的应该只有塔 |
| `foundation` | `body` / `top` / `edge` | 地基已并入地面，所以它必须跟着 `ground` 走；用共用一套灰会重新读成"压在地面上的一块板" |
| `building` | 楼层色板，**按层数循环取用** | 见下面「塔身配色」一节。这是「低幼感」的主战场，三条规则不能违反 |
| `buildingEdge` / `buildingShade` / `buildingLight` | 描边 / 暗面 / 受光面 | 这三层一起构成楼层的体积感。暗面太浅会退回"乐高积木"的观感 |
| `window` / `windowLit` | 塔身窗格、亮着的窗格 | 窗格排布在 `towerView.js` 的 `WIN_COLS` / `WIN_ROWS`，不在主题里 |
| `perfectCap` | 完美落点那一道高光帽 | 三套主题各自取色，别都用金色（夜里金色会糊） |

#### 塔身配色：三条规则

`building` 是整幅画里最容易被改坏的一处。曾经它是**六个色相循环**，在扁砖上像彩色条纹还过得去，方块化之后直接成了**一摞彩虹积木** —— 那是「低幼感」最大的来源。诊断的结论是：**不是颜色丑，是变化太频繁**。低幼来自「多」，艺术感来自「少」。

1. **同一色相，只分三档明度。** 颜色用来「指明这是塔」，不是「让每层颜色都不一样」。
2. **中档取明度的算术中点，顺序排成 中 → 浅 → 深。** 这样相邻层的明暗是「+d、−2d、+d」的等步长上下交替，节奏均匀；三档不等距、或按 `浅 → 中 → 深` 排，都会让某些层界忽然糊掉、或读成塔在朝一个方向褪色。
3. **最亮的一档不能亮过地平线附近的天空。** 塔是前景、天空是背景，前者更亮会失去纵深。白天主题的天空下端约 0.85 明度，所以那套色板的最亮档停在 0.73 左右。

另外两条附带的：

- **`perfectCap` 不能出现在 `building` 里。** 金色压顶是玩家该独占的奖励信号，把它当成普通楼层色会立刻和 HUD 的连击徽章打架。
- **环境（`ground` / `skyline`）不要比塔更饱和。** 白天的草地原来是最饱和的一档，只有它在喊；降成鼠尾草绿之后塔才成为主角。

改配色不必靠色号空想，跑一遍对照图：

```bash
NODE_PATH=$CANVAS_NODE_PATH node dev/compare-palette.js --theme day
# 五版对照：改前六色相 / 当前三档 / 两档 / 单色 / 三档+强调色
```

（`$CANVAS_NODE_PATH` = 装了 `@napi-rs/canvas` 的那个 `node_modules`，装法见 README 的「不开界面直接出图」；它已是默认解析路径时可以整个前缀省掉。）

五版全部由**当前主题的色板按规则推导**，所以换主题也能跑；唯独「改前 · 六色相」是写死的，留作反面教材。

**塔身的形态**（`towerView.js` 顶部的三个常量，都是占一层楼宽/高的比例）与配色同等重要 —— 配色只解决「花」，这三项解决「稚」：

| 常量 | 值 | 作用 |
|---|---|---|
| `SIDE_W_RATIO` | 0.16 | 右侧暗面占宽。低于 0.14 就只是一道脏边，读不出「这栋楼有厚度」 |
| `WIN_COLS` / `WIN_ROWS` | 3 / 3 | 窗格。密格（4×4）读作「网格贴图」，少而长的窗才读作「塔楼立面」 |

#### 改之前必读的六条约束

1. **天体要落进 HUD 与吊车轨道之间的夹缝。** 竖屏里上方是 HUD、下方（约 40% 高度处）是吊车轨道，两道横线之间只剩约 90px。三套主题的天体位置都是照着这条缝定的——改之前先看一遍出图，否则太阳会盖住「机会」指示点、或吊绳从太阳正中穿过。
2. **星辰必须随高度淡出。** 越靠近地平线天光越亮，那里出现星点会很假。`sky.js` 里按 `y` 做了淡出，纵向范围也压在上半部偏下一点；改 `y` 的分布时要连带检查这两处。
3. **云形是「中间鼓、两侧扁」**（`bulge = sin(t·π)`），不是随机半径排一排——后者会得到一条扁平长条，不像云。
4. **城市与星辰的窗灯必须一次 path 批量填充**（`beginPath` + 多个 `ctx.rect` + 单次 `fill`），不能逐窗 `fillRect`。夜景有上百扇窗，逐个 draw call 会直接把帧率吃穿。
5. **天体光晕的衰减要按峰值 alpha 的「比例」，不能写成 `withAlpha(glow, 0.35)`。** 后者是把 alpha **设成** 0.35，而峰值本来就是 0.38 —— 两者几乎相等，于是从圆心到半径的 45% 处几乎是平的，整片光晕被拉平成一顶「锅盖」，在深色夜空里能看出一圈清晰的硬边，读起来像聚光灯而不是月亮。主题只负责给出峰值 alpha，衰减的形状由 `sky.js` 的 `FALLOFF` 负责（配套工具是 `draw.alphaOf`）。
6. **判断颜色与分界一律用采样，不要用眼睛看缩略图。** `dev/probe-pixels.js` 就是为这件事写的：曾经从缩略图上误判 HUD 卡片是白色，差点推翻一套其实正确的配色（实测 `38,41,79`）。扫一条竖列还能把几何关系钉死 —— 例如「塔底 729、地基自 730 起、地面从 730 连续铺下去」这种贴合关系，肉眼看是看不出来的。

```bash
node dev/probe-pixels.js dev/shots/day-ground.png --col 187   # 扫一列，把颜色分界打出来
node dev/probe-pixels.js dev/shots/night-idle.png --at 18,70  # 只看一个点
```

#### 验证回路

```bash
NODE_PATH=$CANVAS_NODE_PATH node dev/render-frame.js --theme all
```

出图落在 `dev/shots/`（已 gitignore）。改完看 27 张图（3 主题 × 9 场景）比开界面快得多。

> **一条硬教训：不要在缩略图上凭肉眼判断颜色。** 曾经据此误判 HUD 卡片是白色（实际采样 `38,41,79`，深蓝紫），差点把整套正确的配色推翻。涉及颜色的结论请用 `getImageData` 采样核对，见 `docs/adr/0006` 的 Consequences。

## 4. 常见目标 → 配方

以下改动都请一次只动一组，改完跑测试、再进开发者工具确认。

**想让整体更难**
```
CRANE.periodSecAtMin       1.5 → 1.25     后期摆得更快
CRANE.periodRampFloors     30  → 20       难度爬升更陡
STABILITY.topHeavyGain     0.06 → 0.10    高塔更危险
TOLERANCE.perfectRatio     0.18 → 0.12    完美线收紧
RUN.missBudget             3 → 2          容错更少
```
注意：一次性全上会难到不可玩。建议一次只改 1~2 项。

**想让整体更宽容（新手友好）**
```
FOUNDATION.width           130 → 170      容错空间线性放大（首选这一项）
STABILITY.collapseRatio    0.62 → 0.72    更抗偏
CRANE.periodSecAtStart     2.2 → 2.8      开局更从容
RUN.missBudget             3 → 5          多几次机会
```
> 优先改 `FOUNDATION.width`：它只影响稳定性判据，不会碰到判定与物理的一致性。

**想让手感更"重"**
```
CRANE.dropGravity          2400 → 3200    下落更快
VISUAL.landingSquash       0.16 → 0.24    压得更扁
VISUAL.missShakePx         7 → 10         抖得更狠
VISUAL.swayAmplitude       5.5 → 8        摇晃更明显
```

**想让节奏更快**
```
FEEL.settleDelaySec        0.12 → 0.06    投得更连贯
CRANE.periodSecAtStart     2.2 → 1.8      摆得更快
```

**想让正反馈更爽**
```
TOLERANCE.perfectRatio     0.18 → 0.24    完美更容易
POPULATION.comboStepBonus  0.35 → 0.5     连击更值钱
SCORE.comboBonusPerStep    5 → 8          追完美更划算
VISUAL.leanVisualGain      0.85 → 1.0    倾斜预警更直观
```

**想让高塔压力更大（后期更刺激）**
```
STABILITY.topHeavyGain     0.06 → 0.09    收紧更快
CAMERA.followRatio         0.8 → 0.86     塔看得更多，但吊车空间更小
```
> 改 `followRatio` 后必须检查吊车轨道有没有和 HUD 撞上。

## 5. 必须成对改的组合

改这几组里的任何一个，都要检查另一个：

| 改了 | 必须一起检查 |
|---|---|
| `FLOOR.width` | 完美容差与失误容差同时变化（都是它的比例）。想只改一个，请改 `TOLERANCE` |
| `CRANE.amplitude` | 必须仍 `< pendulumLength`，且仍 `> 两层坍塌阈值` |
| `CRANE.pendulumLength` | 必须仍 `> amplitude`，且仍 `< pivotHeightAboveTop` |
| `CRANE.pivotHeightAboveTop` | 必须仍 `> pendulumLength` |
| `VISUAL.landingSquashSec` | 必须仍 `< FEEL.settleDelaySec` |
| `CAMERA.topPadding` / `followRatio` | HUD 与吊车轨道是否重叠、吊车是否被状态栏遮住；**这两道横线之间就是天体要落进的那道夹缝**，改窄了记得回去看 `themes.js` 的 `celestial` |
| `FOUNDATION.width` / `STABILITY.collapseRatio` | `CRANE.amplitude` 是否仍能覆盖到坍塌临界位置 |
| `STABILITY.topHeavyGain` | 塔变重后阈值收得更紧，确认 `amplitude` 仍够得到 |
| `WORLD.width` | 所有水平尺度参数的合理值（`centerX`、`amplitude`、`groundBaselineOffset`） |
| `themes.js` 的 `celestial` | `x` / `y` / `radius` / `glowScale` 四者要一起看：半径变大或光晕放大后可能又压到 HUD 或轨道 |
| `themes.js` 的 `building[]` | `buildingShade` / `buildingLight` 的深浅要跟着色板明度调；浅色板配过深的暗面会发脏。三档要**重新拉开等步长**（见第 3.12 节的三条规则），不能只换色号 |
| `FLOOR.radius` | `towerView.js` 的 `SIDE_W_RATIO` 与窗格内缩都按它算（`inset = radius * 0.8`）：圆角改大后明暗带要跟着内缩，否则会从圆角处露出方角 |
| `WIN_COLS` / `WIN_ROWS` | 亮窗的散列公式 `(index * 5 + c * 3 + r * 2) % 7`。换成偶数模数会把行号项消掉，同一层的亮窗会落到同一列上、连成一条竖光带 |
