# 视觉主题：天空是有内容的舞台，且主题不进 config

用户反馈「页面风格太简陋」。诊断下来主因不是配色难看，而是**画面的一大半是空的**：竖屏里天空约占 65% 的高度，此前它只是一段纯色渐变；城市只有一层剪影，淡到几乎看不见；吊车轨道是一条横贯全屏的纯色细线；楼房是纯色圆角块，没有明暗。配色本身没有问题——问题是**没有东西可看**。

这一版做了三件事：把天空做成有内容的舞台（天体 + 光晕 + 云 + 星），把城市做成三层并加大气透视，把楼房与钢梁做出体积感。同时把全部颜色收进三套**完整主题**（晴日 / 黄昏 / 夜晚）。

## Considered Options

- **主题写进 `js/core/config.js`（如 `config.theme = 'dusk'`）**：调参文件是「唯一需要改的地方」，看起来顺理成章。舍弃它的原因：**config 是内核的**，而内核零 `wx` 依赖、也不知道 Canvas 存在（见分层纪律）。主题是纯观感数据，判定不读它。放进去会让内核为渲染的方便买单。
- **每套主题各写一份 `palette.js`，靠改文件切换**：最直白。舍弃它的原因：三份文件之间会漂移（改了一处忘了另两处），而主题的价值恰恰在于「同一套结构、不同取值」。
- **主题数据集中在 `themes.js`，`palette.js` 只负责导出当前主题（选定）**：渲染层其余模块照旧 `require('./palette')`，拿到的始终是一个结构完整的主题。换皮肤不改任何绘制逻辑，也能把任意一套主题直接传给渲染函数——出图工具正是这么做的，用来横向对比。
- **天体位置锚定地平线**：落日贴在城市天际线上，物理上更正确。舍弃它的原因：地平线会随塔高滚出屏幕下方，锚定它等于让太阳跟着往下跑，最终出现在塔的中部。天体是远景，**相机升高时它在画面里的位置本就不该动**，所以用屏幕高度比例。

## Consequences

- 主题只影响观感，**不参与任何判定**。判定参数仍在 `js/core/config.js`；两者的边界就是「内核不知道 Canvas 存在」这条纪律。
- 天体位置（`celestial.x` / `celestial.y` / `radius` / `glowScale`）必须同时避开顶部 HUD 与吊车轨道。白天主题的天空其实只剩约 90px 的夹缝，太阳的大小与高度是照着这条缝定的。`themes.js` 里已注明「改之前先看一遍出图」——靠心算很容易又压到 HUD 上。
- 城市窗灯是逐帧重画的背景，数量必须可控：窗格用**一次 path 批量填充**，而不是上百次 `fillRect`。见 `scene.js` 的 `drawLayer`。
- 多了一条本机特有的验收链路：`dev/render-frame.js` 用原生 Canvas 直接出图。它存在的原因是本机装不了微信开发者工具、浏览器又被安全模块拦截（Chrome 连 `--version` 都 core dump）。它驱动的是 `js/` 下**同一份**渲染代码，所以出的图就是真画面。
- 该出图工具依赖 `@napi-rs/canvas`，这是本工程唯一的 Node 侧外部依赖，且只出现在 `dev/`，不进小游戏包。
- **一个反复踩到的坑**：在缩略图上凭肉眼判断颜色会出错。曾据此误判「HUD 卡片是白色的」，实际采样是 `38,41,79`（深蓝紫），代码从头到尾都是对的。涉及颜色的结论一律用像素采样核对。
